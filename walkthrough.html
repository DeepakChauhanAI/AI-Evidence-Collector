Zero Manual Evidence Hunting

Autonomous Multi-Surface Discovery

The hardest part of compliance was never collecting evidence — it was working out which file or API actually proves each control. The discovery engine does that step, so the operator confirms suggestions instead of typing URLs.

Surface A

Documents & S3

Walks a local compliance folder and lists an S3 bucket. Reads text from .md/.txt/.csv, .docx (stdlib) and .pdf.

Collector: local_file / s3_file
Surface B

Cloud — AWS

A catalogue of 19 read-only checks — IAM password policy, MFA, CloudTrail, KMS, GuardDuty, CloudWatch alarms, RDS backups, ELB, Route 53.

Collector: aws / github
Surface C

Web & Wiki

Crawls a trust centre's sitemap.xml or its own links, keeping same-host compliance pages (/security, /subprocessors).

Collector: document / screenshot
Surface D

Scanned PDFs

Documents with no text layer — signed acknowledgements, photographed policies — are rendered and read by a vision model. Opt-in only.

Opt-in: DISCOVERY_VISION_OCR

How a match is decided

The control's wording is expanded through a compliance thesaurus (access → iam, password, credential), then matched against each asset's name, path and extracted text. The score is the fraction of concepts satisfied. 

score = concepts_hit / concepts_in_control

reason = "matched evidence signals: access, mfa, factor"
signals = { matched_terms, surface, ext, age_days, tier }

✦ No AI confidence percentage. An LLM's self-reported "96%" is not calibrated, and a green badge the auditor stops questioning is worse than no badge.

What a suggestion does — and doesn't do

  • ✓ Suggest — a candidate is a staging row, never a live binding.
  • ✓ Confirm — "Bind" creates an ordinary collector mapping, identical to typing one by hand.
  • ✓ Run — collection is always a separate, explicit action. Discovery never auto-schedules.
  • ✓ Explain — every candidate records its surface, its matched signals, and the asset it came from.
  • ✓ Degrade — with no AWS or GitHub credentials the connected check still runs, but stores a clearly-labelled Sample rather than pretending to be real evidence.

Measured, Not Asserted

python -m app.eval_discovery writes a review sheet of every suggestion for hand-labelling, then reports the split. This is what decided against putting an LLM in the matching path.

SOC 2 Starter Checklist (20 controls) Result What it means
Controls receiving a suggestion 18 / 20 · 90% The two misses need documents no API can evidence (board minutes, code-of-conduct acknowledgements).
Top-1 suggestion correct 15 / 20 · 75% Judged as an auditor would: is this reasonable evidence for this control?
A correct answer within top-3 16 / 20 · 80% The shortlist usually contains the right answer even when it isn't first.
Failures that are ranking errors 1 / 20 The right answer was in the list, just ordered wrong. An LLM rerank could fix this — and only this.
Failures that are recall errors 4 / 20 Nothing correct was found at all. Reordering cannot help; wider coverage can.

Why this matters: a smarter matcher was projected to lift quality, but the measurement showed only 1 of 20 failures was a matching problem — adding six AWS descriptors fixed 3. The bottleneck is discovery coverage, not match judgement. Labels are the reviewer's judgement, not an auditor's; the ranking-vs-recall split is robust to that.

Who Does What: Engine vs Agent

Discovery is deliberately not driven by the LLM. Finding and matching must be reproducible — the same folder and checklist must produce the same suggestions on a re-run, or the audit trail is worthless.

Step Handled by Uses AI? Why
Walking folders, listing buckets, crawling a wiki discovery/document_scanner.py, web_crawler.py No File and HTTP operations — an LLM adds nothing.
Deciding which asset matches which control discovery/matchmaker.py No Reproducible, auditable, and free. Measured at only 1 ranking error in 20.
Reading a scanned page with no text layer discovery/ocr.py + vision model Yes (opt-in) The only way to read a scan — no parser can.
Choosing a collector type and drafting its config checklist.suggest_collector(), agent.draft_config() Yes Semantic judgement over control intent.
Grading collected evidence against the control agent.assess_evidence() Yes Reading prose and reporting gaps is genuinely a language task.

⚠️ Vision OCR is off by default — deliberately

Enabling DISCOVERY_VISION_OCR=true sends page images of your documents to the configured LLM endpoint. That is the only place in discovery where document contents leave the machine, so it never turns itself on. Everything else — folder, S3, the AWS/GitHub catalogues, the web crawl, and PDF/DOCX text extraction — stays local and deterministic. Results are cached by file hash, so re-scanning does not re-send pages.

Internal Intelligence Core

The Four Roles of the AI Agent

All AI reasoning is isolated in agent.py and checklist.py — the discovery engine itself is deterministic and reproducible. The application pairs high-level intelligence with deterministic safeguards.

1. Collector Mapper

Reads control titles and descriptions to select the exact right collector type (AWS, API, Doc, or Screenshot).

checklist.suggest_collector()

2. Config Author

Drafts compliant JSON configurations matching target collector schemas, complete with realistic endpoints.

agent.draft_config()

3. Auditor Evaluator

Inspects gathered artifacts against compliance text, calculating satisfaction, gap commentary, and confidence scores.

agent.assess_evidence()

4. Autonomous Planner

Accepts natural language goals, plans the collector vector, generates config, and stamps the plan into audit metadata.

agent.plan_collection()

Graceful Degradation: Zero-Crash Guarantee

Agent Role When AI is Connected (OpenAI / DeepSeek) When AI is Offline (No API Key / Outage) System Safety Impact

Config Author Customized JSON parameters tailored to specific systems. Pre-defined schema template skeletons. Operator fills in blank
Auditor Evaluator Automated gap analysis, audit summary, confidence score. Raw artifacts preserved; pending human reviewer flag. Evidence preserved safely

Plug & Play Data Ingestion

The Evidence Collectors

All evidence collection is deterministic, auditable, and immutable. No unpredictable scraping or hallucinations. The discovery engine suggests which of these answers a control; the collector itself only ever fetches.

AWS Collector (aws)

Boto3 SDK

Direct read-only describe/list/get calls against AWS IAM, CloudTrail, S3, KMS, GuardDuty, CloudWatch, Auto Scaling, Backup, RDS, ELB and Route 53. 

{
  "service": "iam",
  "operation": "get_account_password_policy",
  "region": "us-east-1"
}

✦ Built-in Sample Mode: Generates representative realistic fixtures when AWS credentials are not yet set.

HTTP API Collector (http_api)

REST / GraphQL

Connects to GitHub, Okta, Jira, Datadog, Cloudflare, or internal microservices over HTTP. 

{
  "url": "https://api.github.com/repos/org/repo/branches/main/protection",
  "method": "GET",
  "headers": { "Authorization": "Bearer $GITHUB_TOKEN" }
}

✦ Secret Resolution: Safely resolves environment secrets (e.g. $API_KEY) at runtime.

Document Collector (document)

PDF / Policy Fetcher

Pulls policy documents, security manuals, exported reports, or Drive attachments over secure HTTP. 

{
  "url": "https://company.internal/policies/info_sec_policy.pdf",
  "filename": "Information_Security_Policy_v4.pdf"
}

✦ Binary Safe: Preserves exact PDF binary integrity with full cryptographic verification.

Screenshot Collector (screenshot)

Playwright Headless

Automates headless Chromium to snap high-resolution proof from web consoles that lack public APIs. 

{
  "url": "https://dashboard.stripe.com/settings/security",
  "full_page": true,
  "wait_ms": 2500
}

✦ Lazy Loading: Imports Playwright only when called so server starts in milliseconds.

GitHub Collector (github)

REST API

Read-only repo and org governance: branch protection, required reviews, Actions workflows, secret-scanning and Dependabot alerts. 

{
  "endpoint": "repos/{owner}/{repo}/branches/{branch}/protection"
}

✦ {owner}/{repo}/{branch} fill from env vars; without a GITHUB_TOKEN it stores a labelled sample instead of calling out.

Local File Collector (local_file)

On-Premise

Reads a document the discovery engine found on this machine — for evidence that never leaves the internal network. 

{
  "path": "./compliance_docs/Access_Control_Policy_2026.md"
}

✦ Path-Guarded: refuses any path outside DISCOVERY_DOCS_DIR, so a bound candidate cannot be repointed at an arbitrary file.

S3 Object Collector (s3_file)

Binary Safe

Fetches a single object from a compliance bucket. Kept separate from the AWS collector because it returns bytes, not JSON. 

{
  "bucket": "acme-compliance",
  "key": "policies/Info_Sec_Policy_v4.pdf"
}

✦ Preserves the object byte-for-byte and records its ETag alongside the SHA-256 digest.

Agent Collector (agent)

Delegating

Given a natural-language goal, plans which real collector to use and with what config, then delegates to it. 

{
  "goal": "collect the IAM password policy for CC6.1"
}

✦ Auditable Plan: the chosen collector and config are stamped into the artifact's metadata.

Writes a review sheet of every discovery suggestion to hand-label, then reports accuracy split by ranking vs recall failure:
